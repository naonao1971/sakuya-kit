# 咲耶シリーズ 新作づくり（企画 → プロト → 公開 → わいわいタウン）

咲耶シリーズの共通の土台「咲耶ゲームkit」（リポジトリ・コード上の名前は `sakuya-kit`）を使って作る。

利用者は、昔のレトロゲームのタイトルをいくつかと、簡単な要件だけを伝えてくる。
この skill は、質問しながら構成を固め、遊べるプロトを作り、磨いて公開し、わいわいタウンに載せるまでを一緒に進める。

## 進め方の原則

- **段階ごとに区切り、利用者の OK をもらってから次へ進む。** 各段階の終わりに「決まったこと／次にやること」を短く出す
- **質問は1回に4つまで。** AskUserQuestion が使えるなら選択肢で聞き、おすすめを先頭に「（おすすめ）」付きで置く。
  決め手が無い細部は聞かずに既定値で進め、何を既定にしたかだけ伝える
- **利用者は開発者ではない前提で話す。** 専門用語を避け、確認してほしいことは「どこを押して、何が起きればOKか」で書く
- **共通部分は必ず sakuya-kit を使う**（ルールは `references/kit-rules.md`。作り始める前に必ず読む）
- **状態は企画書に残す。** 決まったことはリポジトリの `docs/PLAN.md` に書き足していく。会話が途切れても、そこから再開できるようにする

## 段階 0: 受け付け

利用者の最初の言葉から、次を拾う。無いものは段階 1 で聞く。

- 元ネタのレトロゲーム（1〜3本）
- やりたいこと（「CNP を集める」「スマホで片手で」など）
- すでに決まっている名前・絵・動画

元ネタごとに `references/retro-catalog.md` を引き、**どの要素を借りるか**の候補を出す。
表に無いタイトルは、知っている範囲で同じ形（中心の遊び・操作・1プレイの長さ・kit の設定）に書き起こす。
複数の元ネタは「Aの操作 × Bの目的」のように組み合わせの案を2〜3個出して選んでもらう。

## 段階 1: ヒアリング

`references/hearing.md` の質問票を上から順に、まだ決まっていないものだけ聞く（最大4ラウンド）。
各ラウンドの後、決まった内容を2〜3行で復唱する。

## 段階 2: 企画書 → 承認

`references/hearing.md` の末尾の「企画書のひな形」で1ページにまとめて見せ、OK をもらう。
ここで必ず決めること: 日本語名・英字の主題と副題・`gameId`・公開 URL（例 `xxx.naoblock.jp`）・操作・クリア条件・スコアの付け方と上限の目安。

## 段階 3: リポジトリの用意

この環境からはリポジトリを新しく作れない。利用者に次を頼む（手順はそのまま渡す）:

1. GitHub で空のリポジトリを作る（名前の案を出す。例 `SakuyaXxx`）
2. Claude の GitHub アプリにそのリポジトリを追加する
3. できたら知らせてもらう

届いたら `add_repo` でセッションに足して clone し、作業ブランチを切る。
`assets/starter/index.html` を `index.html`、`assets/starter/sw.js` を `sw.js` として置き（機内モード対応）、企画書の値（`gameId`・名前・操作）を入れる。
`docs/PLAN.md` に企画書を置く。README に「sakuya-kit を使っている／遊び方／操作」を書く。
sakuya-kit も手元に clone しておく（プレイテストで CDN の代わりに使う）。

## 段階 4: プロト（遊べる最小版）

**目的は「中心の遊びが面白いか」を早く確かめること。** 絵はまだ仮でよい（canvas の図形、`kit.cnp` の絵）。

- 入れるもの: 自機の操作、中心の遊び1つ、ミスとゲームオーバー、スコア、クリア（またはエンドレスの終わり方）
- 入れないもの: 演出動画、凝った背景、OGP、細かい調整
- 動かして確かめる: `scripts/playtest.mjs`（PC とスマホ横持ちで、開始・プレイ・一時停止・ゲームオーバー・クリア・縦持ちを通し、エラーと画面写真を出す）
  ```
  node <skill>/scripts/playtest.mjs --game <リポジトリ> --kit <sakuya-kit> --out <作業フォルダ>
  ```
  画面写真を自分で見て、崩れや読めない文字が無いか確かめてから渡す
- push して、実機で遊べる URL を渡す: `https://raw.githack.com/<owner>/<repo>/<ブランチ>/index.html`
- 利用者の感想を聞く質問は「速さ／難しさ／操作のしやすさ／もっと欲しいもの」の4つまで。直して、また URL を渡す。
  「中心の遊びがこれでよい」と言われるまで、この段階を繰り返す

## 段階 5: 仕上げ

企画書の残りを入れる。順番は、遊びに近いものから:

1. ステージ・敵・難易度の流れ、CNP 11体の出し方（全員そろえるとボーナス、など）
2. HUD（`kit.hud`）、効果音（定番は `kit.sfx`、固有の音だけ自前）、BGM（任意）
3. 結果画面の飾り（`resultScreen.decorate`：ボーナスの内訳・救出した CNP）
4. 演出動画（任意。利用者が mp4 を用意したら `cutscenes` に渡すだけ）
5. シェア（`share`。文言とハッシュタグ、1200x675 のカード絵は任意）
6. スコアの上限を決める: 理論上の最高点を計算し、少し上の切りのよい数を `maxScore` にする

段階ごとに playtest を回し、URL を渡して確認してもらう。

## 段階 6: タイトル・OGP・アイコン

- キービジュアル（横長の絵）を利用者にもらう。無ければ、タイトル画面の canvas を書き出して仮に使う
- `scripts/make-assets.mjs` で ogp.png・アイコン・favicon・manifest.json・`<head>` をまとめて作る（tools/ogp.html と同じ部品を使う）
  ```
  node <skill>/scripts/make-assets.mjs --game <リポジトリ> --kit <sakuya-kit> --visual <絵のパス> \
    --title "SAKUYA XXX" --subtitle "- XXX -" --name-ja "咲耶XXX" --desc "説明文" --url "https://xxx.naoblock.jp/"
  ```
- `CNAME` に公開ドメインを書く

## 段階 7: 本番公開

`references/release.md` の「本番公開」の順に進める。利用者の手が要るもの（スプレッドシートの `_games` の行、
GitHub Pages の設定、DNS）は、押す場所まで書いた手順で頼む。公開前チェックリストを全部通してから PR をマージする。

## 段階 8: わいわいタウン掲載と告知

`references/release.md` の「わいわいタウン掲載」の順に、**掲載用のパック**（作品名・紹介文・遊び方・操作・タグ・
サムネイル・URL・権利表記）を作って渡し、登録画面の入力を一緒に進める。登録そのもの（ログインと送信）は利用者が行う。
最後に X の告知文を作る（x-post-generator の skill があれば使う）。

## この環境でできないこと（先回りして利用者に頼む）

- リポジトリの新規作成（段階 3）と、GitHub アプリへの追加
- タグ・リリースの作成（push が切れる）: kit の新しい版は、利用者に GitHub の画面で Release を作ってもらう
- Google Apps Script とスプレッドシートの操作（`_games` シートの行の追加など）
- jsDelivr・script.google.com・わいわいタウンへの接続（プレイテストでは CDN を手元の kit に差し替える）
- H.264 の動画の再生（テストのブラウザでは流れない。動画は実機で確かめてもらう）
- わいわいタウンへのログインと登録の送信

## 既存タイトルを直すとき

段階 4〜7 の手順（playtest → URL で確認 → PR → マージ）だけを使う。kit に足りない機能は kit 側に足す（`references/kit-rules.md`）。
